# 후속 개발 계획

1.0.0 이후의 개발·조사 기록입니다. 상하좌우 조작은 릴리즈 후보 1.1.0-rc.1에 추가했으며, 나머지 기능은 아래 상태에 따라 보류합니다.

현재 카메라 제어 범위는 **상하좌우 방향 조작**으로 한정합니다. 사용자는 실제 동작을 확인한 이 기능만으로 우선 충분하다고 정했습니다. 개발 버전과 기능별 간단 검사 명령은 [개발 안내](development.md)를 참고하세요.

렌즈 숨기기·복원과 저장 위치의 추가 조사는 추후로 미룹니다. 음성 시험도 사용자 요청으로 보류합니다. 줌은 제외하고 알림·소리 증폭은 후순위로 둡니다. 상하좌우 조작은 별도 시험 도구에서 실물 확인했고, 앱 UI와 개발용 EXE에 통합했습니다. 앱에서도 실제 이동을 사용자에게 확인받았으며, dev.3 조작감에 대해 “지금은 괜찮은 것 같다”는 평가를 받았습니다. 공개 1.0.0 배포본은 그대로 유지합니다.

## 카메라 제어

우선 검토 대상은 **ipTIME C500GS · 펌웨어 37.0.161**입니다. 모델·설치 버전은 사용자가 제조사 앱에서 확인한 정보입니다. 제조사 앱에서 가능한 기능이 CamFloat에서도 가능한지는 별도 검증이 필요합니다.

| 기능 | 확인할 내용 |
| --- | --- |
| 방향 전환·저장 위치 | ONVIF PTZ 등 외부 인터페이스, 이동·정지·저장 위치 명령 |
| 확대·축소 | 광학 줌 지원 여부. 영상의 디지털 확대는 별도로 검토 |
| 렌즈 숨기기·복원 | 제조사 앱 OFF/ON과 같은 위치 이동. 사용자 관찰상 영상·마이크는 계속 동작하므로 전원·음성 차단으로 표시하지 않음 |
| 마이크로 말하기 | 음성 전송 경로·인증·지원 코덱·지연 |

위 표의 저장 위치·렌즈 숨기기·말하기는 조사 기록 보존용이며 이번 방향 조작 범위에 포함하지 않습니다. 줌은 개발 대상에서 제외합니다.

### 방향 조작 UI 합의

- 스크린 빠른 메뉴는 새로고침 → 음량 → 카메라 이동 → 카메라 지정 → 전체화면 순서입니다. 카메라 지정은 전체화면 바로 왼쪽에 둡니다.
- `카메라 이동` 아이콘을 누르면 해당 스크린의 방향 패널을 엽니다. 별도의 방향 조작 사용/사용 안 함 설정은 추가하지 않습니다.
- 넓은 스크린은 십자 배치, 작은 스크린은 `← ↑ ↓ →` 가로 한 줄로 표시합니다. 기준은 앱 전체 크기가 아닌 해당 스크린 크기입니다.
- 작은 스크린의 하단 빠른 메뉴도 한 줄을 유지하고 버튼 간격·크기를 줄여 화면 밖으로 나가지 않게 합니다. 음량은 기존 작은 스크린용 팝업을 유지합니다.
- 방향 버튼을 누르는 즉시 짧게 이동하고, 길게 누르는 동안 약 160ms 간격으로 명령을 갱신합니다. 손을 떼면 갱신을 멈춥니다. 패널을 연 스크린의 카메라를 대상으로 하며 기존 방향키의 SCREEN·카메라 전환은 유지합니다.
- 조작 중 패널을 유지하고 바깥 클릭·ESC·다른 앱으로 전환·화면 카메라 변경 시 닫습니다. 선택 테두리와 패널 열림은 별개로 처리합니다.
- 우클릭 메뉴에도 동일한 아이콘과 `카메라 이동` 이름을 사용합니다. 개발본에 구현했으며 아래 ONVIF 시험 도구와 프로토콜 코드를 공유합니다.

### 개발본 통합 상태

현재 후보는 **1.1.0-rc.1**입니다. 전체 회귀 207개·합성 RTSP 4개 복구/소리/65초 연속 재생·압축 해제 EXE 검사를 통과했습니다. 자동 검사는 실제 카메라의 물리적 멈춤을 대체하지 않으며 최종 사용자 확인 후 1.1.0으로 공개합니다. 자세한 결과는 [검토·검사 요약](../CODE_REVIEW.md)을 참고하세요.

- `onvif_control.py`의 인증·프로필 탐색·시간 제한 이동을 앱과 시험 도구가 공유합니다. 앱 대상은 내부망 IPv4 주소로 등록한 카메라입니다. 최초 조회는 확인된 5000번 서비스에서 시작하고, 같은 카메라 IP가 응답한 유효한 제어 포트·경로는 사용합니다. 다른 IP·외부 주소·도메인은 아직 지원하지 않습니다.
- `ptz_control.py`는 등록 최종 저장 후 제어 경로·프로필 식별자를 비동기로 최초 조회합니다. 기존 카메라는 첫 패널 열기 때 확인하며 패널은 기다리지 않고 저장된 값 또는 C500GS 기본값으로 즉시 준비합니다. 조회 실패도 등록·재생을 막지 않고 기본값을 유지합니다. 패널을 닫아도 정보는 보존하며 주기적으로 조회하지 않습니다. 이동 요청은 대기열에 쌓지 않습니다.
- 제어 정보는 주소·계정이 바뀌면 무효화되도록 연결에 묶어 로컬 설정에 DPAPI 암호화 저장합니다. 카메라 목록 내보내기에는 포함하지 않습니다. 실제 전송 실패·HTTP 오류·SOAP Fault 때 정보만 재조회하고 이동은 자동 재전송하지 않습니다. dev.3에서는 전송 후 응답 지연·종료·예상과 다른 응답을 조작 실패로 단정하지 않으며 방향 버튼·길게 누르기를 유지합니다. 미확인 응답을 정상 응답으로 기록하지 않고 최근 응답 결과만 메모리에 보관합니다. 갱신한 정보는 다음 사용자 입력에 적용합니다.
- 앱은 별도 `Stop` 요청과 그 응답 대기를 제거했습니다. 각 이동에 `PT0.25S` 제한을 사용하고 이동 응답 대기는 150ms로 제한합니다. 길게 누르기는 약 160ms 간격이며 진행 중 요청이 있으면 추가 요청을 쌓지 않습니다. 손 떼기·버튼 영역 이탈·패널 닫기·앱 전환 시 반복을 중단합니다.
- **실물 확인 필요:** 기존 시험은 시간 제한과 정지 요청을 함께 사용했습니다. 정지 요청 없는 자동 멈춤과 길게 누르기의 부드러움은 새 앱에서 사용자가 렌즈를 보며 확인해야 합니다. 시간 제한을 기기가 준수하는 경우 손을 뗀 뒤 마지막 요청의 남은 시간만큼 이동할 수 있으며, 이를 모든 카메라에서 보장하지 않습니다. 기존 수동 조사 도구의 명시적 정지 처리는 유지합니다.
- 카메라 지정 변경·패널 닫기·앱 전환은 이전 작업을 무효화합니다. 이전 연결 확인이 늦게 끝나도 이동을 예약하지 않고, 앱 종료는 진행 중인 작업의 정리까지 기다립니다.
- 방향 패널이 열려 있는 동안 상단바를 숨겨 좁은 화면의 가림을 방지합니다. 화면 크기에 따라 패널을 다시 배치하고, 기존 방향키·전체화면·화면 확대 규칙을 유지합니다.
- dev.2의 기본·방향·등록·목록 파일 관련 검사 86개와 창·분할·메뉴 관련 검사 19개를 통과했습니다. 가상 카메라를 사용한 검사이며 실제 카메라 이동의 재검증 결과는 아닙니다. 공통 프로토콜로 등록 내부망 카메라 한 대의 기능·프로필 조회는 정상 응답을 확인했고 이동·음성 요청은 보내지 않았습니다. 일반 수정에 맞춰 전체 회귀·장시간 재생 QC는 실행하지 않았습니다.
- dev.3은 사용자가 보고한 “이동은 되지만 응답 미확인 안내로 방향 버튼이 사라짐”을 수정했습니다. 전송 뒤 시간 초과·연결 종료·예상과 다른 응답을 모의해 패널 유지·길게 누르기·연타·손 뗀 뒤 반복 중단을 포함한 관련 검사 61개를 통과했습니다. 응답 미확인 상태를 이동 불가능·이동 성공 어느 쪽으로도 단정하지 않습니다.
- **사용자 평가:** dev.3에서 빠른 연타 중 진행 중인 요청이 있으면 새 입력을 건너뛰는 현재 방식에 대해 “괜찮은 것 같다”고 확인했습니다. 현재 입력 처리와 갱신 간격을 유지합니다. 이 평가는 조작감에 대한 확인이며, 시간 제한 준수의 정량 측정·모든 방향/환경의 전체 QC를 수행했다는 의미는 아닙니다.
- 개발 EXE를 별도 설정 폴더에서 `--self-check`로 실행해 시작·번들 엔진·창/메뉴·관리창 진입을 확인했습니다. 이 검사는 영상 재생·음성·실물 방향 조작 검사가 아닙니다. 실행 중인 CamFloat를 종료한 뒤 개발본에서 내부망 카메라의 이동 아이콘을 눌러 네 방향 이동과 멈춤을 확인해야 합니다.

### 사전 조사 결과

제조사 앱의 기능과 외부 제어 API는 구분합니다. [37.0.161 공식 배포 안내](https://www.iptime.com/support/downloads/27522)에 C500GS가 포함되어 있습니다. 공식 고객지원은 [C500GS의 PC 멀티뷰어 PTZ 미지원](https://iptime.com/support/qna/892695)을 안내했으며, 이것이 모든 외부 제어 경로가 불가능하다는 뜻은 아닙니다.

등록된 내부망 카메라 2대에 **조회만 수행**한 결과입니다. 다른 모델·네트워크까지 확인한 결과는 아닙니다.

| 조회 | 결과와 해석 |
| --- | --- |
| RTSP 접속 정보 | 두 기기 모두 Digest 인증 후 설명 조회 성공. 영상 H.265, 수신 음성 G.711 A-law 8 kHz 확인 |
| 마이크 전송 통로 | ONVIF backchannel을 요청해도 일반 조회와 같은 영상·음성 목록만 반환. 별도 전송용 음성 트랙과 방향 정보가 없어 표준 방식의 지원은 미확인 |
| 장치 정보·서비스 | 최초 비인증 SOAP 조회는 연결 종료. 이후 인증을 포함한 기능·프로필 조회에는 정상 ONVIF 응답 확인. 일부 조회는 여전히 연결 종료 |
| 자동 발견 | 알려진 기기 주소에 보낸 WS-Discovery 단일 대상 조회에는 응답 없음. ONVIF 미지원으로 단정할 수 없음 |
| RTSP 확장 | `USER_CMD_SET` 등 확장 명령을 광고함. 회전·말하기에 활용 가능한지는 미확인 |

[ONVIF 스트리밍 규격 5.3](https://www.onvif.org/specs/stream/ONVIF-Streaming-Spec.pdf)은 backchannel 요청 시 전송용 미디어와 방향 정보를 구분하도록 합니다. 단순한 `200 OK` 응답은 말하기 기능의 확인으로 취급하지 않습니다. `/onvif1`이라는 영상 경로도 ONVIF 제어 지원의 근거가 되지 않습니다.

비교 자료인 [Yoosee 회전 제어 구현](https://github.com/realldz/onvif_proxy_server)과 [말하기 구현](https://github.com/realldz/yoosee-intercom)에서 같은 RTSP 확장 명령을 사용합니다. **호환성 조사 후보**이며 ipTIME에서 동작한다는 증거는 아닙니다. 외부 코드 자체는 실행하지 않았습니다.

### 실제 회전 요청 시험

사용자 요청으로 내부망 기기 한 대에 RTSP 회전 요청을 시험했습니다. **짧은 RTSP 후보 명령으로는 실제 회전을 확인하지 못했습니다.** 수동 시험에서 5가지 방식을 선택했고, 이동 요청까지 전송된 5회는 모두 `200 OK`였지만 사용자 관찰은 전부 “움직이지 않음”이었습니다. 나머지 이동 시험 5회는 사전 연결·정지 검사 중 시간 초과로 이동 요청을 보내지 못했습니다. 정지 응답도 물리적 정지 지원의 증거로 취급하지 않습니다.

이는 0.18초 이동 요청과 해당 후보 형식에 대한 결과입니다. 응답만 반환하고 명령을 처리하지 않는 경우, 형식·인증·이동 시간 등 다른 조건을 구분하지 못했으므로 기기 전체의 외부 제어 미지원으로 단정하지 않습니다. 현재 방식은 앱에 통합하지 않고 조사 도구로만 둡니다.

추가 영상 연결을 연 상태에서는 두 번째 제어 연결의 인증·사전 검사에서 `400`이 발생해 이동을 보내지 못했습니다. 영상 연결을 추가하지 않은 요청 시험은 통과했습니다. 동시 연결 수와 인증 처리의 영향이 의심되지만 원인은 확정하지 않았습니다. 영상의 밝기·픽셀 변화는 성공 판정에 쓰지 않았습니다.

이전 RTSP 시험 도구 소스와 결과는 유지합니다. 기본 BAT 실행 경로는 아래 ONVIF 시험으로 변경했습니다.

### 후속 ONVIF 조사와 시험 도구

[C400G 전용 공개 구현](https://github.com/wonjj6768/c400g-ptz)을 단서로, 표준 [ONVIF 인증](https://www.onvif.org/specs/core/ONVIF-Core-Specification.pdf)으로 추가 조회했습니다. C500GS에서 해당 라이브러리 자체를 설치·실행한 것은 아닙니다.

- 내부망 기기 2대 모두 UsernameToken PasswordDigest를 포함한 `GetCapabilities`·`GetProfiles`에 정상 SOAP 응답을 반환했습니다. PTZ 기능과 PTZ 설정이 연결된 영상 프로필 2개를 확인했습니다.
- 기기가 알려준 PTZ 서비스 경로가 일반적인 경로와 달랐습니다. 도구는 기기가 반환한 경로를 먼저 사용하고, 필요시 일반 PTZ 경로도 사용자가 선택할 수 있게 합니다. 계정 정보 전송은 동일 기기의 확인된 5000번 포트로 제한합니다.
- `GetNodes`·`GetStatus`·`GetConfigurationOptions`·`Stop` 등은 시험한 요청에서 정상 응답을 확인하지 못했습니다. 연결 종료를 명령 성공으로 취급하지 않습니다. C400G 공개 구현에도 유사한 예외 처리가 있지만 실제 동작은 직접 관찰로 구분합니다.
- 제조사 앱 통신은 캡처하지 않았습니다. USB로 설치 APK를 확보해 C500GS의 통신 경로를 정적으로 조사했습니다. 사용자 수동 시험에서 ONVIF 상하좌우 이동과 실제 멈춤을 확인했습니다.

**초기 수동 ONVIF 시험 결과:** C500GS · 37.0.161 기기 한 대에서 수평 양방향 회전과 실제 멈춤을 사용자 관찰로 확인했습니다. 이동 시험 6회 중 정상 이동 SOAP 응답 5회, “움직이고 멈춤” 4회, 관찰 미확인 1회, “움직임 없음” 1회였습니다. 기기가 반환한 PTZ 경로에서는 4회 모두 정상 이동 응답을 받았고, 3회는 실물 동작 확인·1회는 관찰 미확인이었습니다. 일반 PTZ 경로의 결과는 일관되지 않아 기본값은 기기가 반환한 경로를 사용합니다.

**추가 상하좌우 시험 결과:** 사용자가 다른 등록 내부망 기기 한 대에서 두 연결 경로의 상하좌우를 각각 시험했습니다. 추가 이동 8회 모두 정상 이동 SOAP 응답과 “움직이고 멈춤” 관찰이 기록됐으며, 대화에서도 “상하좌우는 잘 된다”고 확인했습니다. 각 경로에서 좌우 2회·상하 2회입니다. 전체 기록의 이동 14회 중 실제 움직이고 멈춤 12회, 관찰 미확인 1회, 움직임 없음 1회이며, 기록은 로컬 `onvif-manual-latest.json`·요약은 `onvif-summary.json`에 보관합니다. 기기 모델·펌웨어는 사용자 제공 정보 기준이며 다른 기종 전체로 일반화하지 않습니다.

명시적인 `Stop` 요청의 정상 응답은 여전히 없었습니다. 이번 시험은 0.25초 기기 시간 제한과 별도 `Stop`을 함께 사용했으므로 **`Stop` 단독 효과는 미확인**입니다. 상하좌우의 짧은 이동과 멈춤은 사용자 관찰로 확인했습니다. dev.2는 짧은 클릭과 길게 누르기를 구분하고, 작업 중 다른 이동을 쌓아두지 않으며 패널 닫기·앱 전환 시 이동 명령 갱신을 중단합니다. 별도 정지 요청은 제거하고 기기의 0.25초 제한을 사용합니다. 앱 조작의 실물 확인과 명시적 정지 단독 효과는 별도 검증이 필요합니다. 다른 기기·펌웨어, 사생활 보호와 말하기 기능까지 지원이 확인된 것은 아닙니다.

**직접 시험:** 프로젝트 루트의 `camera-control-test.bat`을 실행하고 카메라 번호를 선택합니다.

1. Enter/R은 좌우 양방향, U/D는 상하 양방향입니다. 기본 3초 대기 후 이동 요청을 보내며 `camera-control-test.bat --delay 10`으로 대기 시간을 지정할 수 있습니다(0~300초). 반전 설정에 따라 실제 방향은 달라질 수 있습니다. 상하좌우의 짧은 이동과 멈춤은 사용자 시험으로 확인했습니다.
2. 0.2초 뒤 별도 연결로 `Stop`을 보내고 마지막 정지도 시도합니다. `ContinuousMove`에는 기기 시간 제한 0.25초도 지정합니다. 기기의 제한·정지 준수는 미확인이므로 렌즈를 보며 시험하고, 멈추지 않으면 제조사 앱에서 정지합니다.
3. Y는 실제로 움직이고 멈춤, N은 움직임 없음, Enter는 미확인입니다. S는 정지 요청, N은 입력 단계에 따라 다른 연결 경로 선택, Q는 종료입니다.
4. `camera-control-test.bat --probe`는 기능 조회만 수행하며 이동·정지 요청을 보내지 않습니다. 기능·프로필 조회에 실패하면 수동 시험도 이동 요청을 보내지 않습니다.

새 결과는 로컬 `verification/current/camera-control/onvif-manual-latest.json`에 번호·이동 축·통신 결과·관찰 결과만 기록합니다. 새 실행도 이전 정상 기록을 읽어 최근 50개를 보존합니다. 조회 전용 결과는 `onvif-probe-latest.json`에 분리해 수동 시험 기록을 덮어쓰지 않습니다. 주소·계정·비밀번호·프로필 토큰·영상·음성은 결과에 넣지 않습니다. 회전 시험 도구는 등록 정보와 저장 위치 설정을 바꾸지 않습니다. 공개 1.0.0에는 제어 기능이 없고, 개발본에는 아래와 같이 방향 조작만 통합했습니다. `check.bat ptz`는 두 시험 도구를 가상 기기로 검사하며 실제 기기에 접속하지 않습니다. 상하 단일 축·기기 시간 제한·정지 예약·중단 시 정지·기록 보존 등을 포함해 25개 검사를 통과했으며, 상하좌우 실물 시험 결과는 별도로 기록합니다.

### 렌즈 숨기기·복원

사용자 관찰상 제조사 앱의 OFF는 렌즈가 숨는 위치로 이동하는 동작이며 스트리밍·마이크를 차단하지 않습니다. CamFloat에서 구현한다면 **렌즈 숨기기 / 복원**으로 의미를 구분합니다. 복원할 사용 위치와 숨김 위치를 확보한 뒤 이동을 시험합니다.

두 내부망 기기의 `GetPresets`·`GetStatus`를 광고된 PTZ 경로와 일반 경로에 요청했으나 모두 응답 없이 연결이 종료됐습니다. 추가로 기기 한 대에서 SOAP 1.1/1.2와 주소 지정 헤더 유무 4가지 조합으로 목록을 조회했으나 같은 결과였습니다.

복원 지점 저장 가능성을 확인하려고 **새 임시 위치 생성 요청 한 번**을 보냈습니다. 기존 위치 식별자는 지정하지 않았고 이동 명령도 보내지 않았습니다. 생성 요청도 응답 없이 종료돼 성공 여부와 삭제할 식별자를 확보하지 못했습니다. 임시 항목이 제조사 앱에 보이면 삭제가 필요하며 이름은 로컬 `verification/current/camera-control/preset-save-probe.json`에 기록했습니다. 응답 없는 생성을 반복하지 않습니다.

현재 위치·복원 위치가 확보되지 않아 숨김 이동은 수행하지 않았습니다. 반복 이동 시간을 누적해 이전 위치를 추측하는 방식으로 복원을 구현하지 않습니다. 제조사 앱의 실제 저장 위치·OFF/ON 경로는 아래 APK 분석으로 조사했으며, Windows에서 사용할 인증·연결 방법과 기기의 실제 실행 확인이 남아 있습니다.

**추가 읽기 전용 조회(2026-10-19):** 이미 방향 조작을 시험한 등록 내부망 기기 한 대에서 `GetProfiles`에 포함된 실제 설정·노드 식별자를 사용했습니다. 기기가 광고한 PTZ 경로와 일반 PTZ 경로 각각에 `GetConfiguration`·`GetConfigurationOptions`·`GetNode`를 요청했습니다. 설정·노드 조회는 연결이 종료됐고, 옵션 조회는 HTTP 200이었지만 정상 옵션 응답이 아니었습니다. 광고 경로의 옵션 응답을 별도로 확인한 결과 SOAP `Fault`였습니다. 오류 세부 원인은 확보하지 못했습니다. 이후 추가 확인에서는 프로필을 다시 읽는 데 실패해 옵션 요청을 보내지 않았습니다. 영상 프로필에도 절대 위치 좌표계·좌우/상하 범위 정보가 없었습니다. 따라서 HTTP 상태와 프로필에 PTZ 설정이 있다는 사실만으로 위치 저장·복원을 제공할 수 없습니다. 이동·위치 저장·음성 요청은 보내지 않았습니다. 로컬 결과는 `verification/current/camera-control/lens-readiness.json`·`lens-options-response.json`에 보관합니다.

**렌즈 숨기기·복원의 다음 조건:** 제조사 OFF/ON 경로의 지원 문서와 Windows에서 사용할 연결·인증 방법, 또는 현재 위치 조회와 저장 위치 이동이 실제로 동작하는 인터페이스가 필요합니다. 같은 실패 조회와 임시 위치 생성을 반복하지 않고 이 정보를 먼저 확보합니다. 별도 ONVIF 위치를 만드는 방식이 가능해지더라도 제조사 앱의 OFF 상태·예약과 동기화되는지는 따로 확인해야 합니다.

사용 휴대폰은 Android로 확인됐습니다. 우선 USB로 승인된 휴대폰에서 `com.cctv.iptime`의 APK만 읽어 SDK·제어 명령의 단서를 조사합니다. `android-app-check.bat`은 해당 패키지의 `pm path`와 APK `pull`만 수행하며 앱 설치·앱 데이터·계정·사진·다른 앱·logcat 수집을 하지 않습니다. APK는 실행하지 않고 ZIP 데이터로만 읽습니다. SDK 표식이나 단어 발견은 호환성의 증거가 아닌 조사 단서입니다.

공식 Google Platform-Tools 37.0.1의 ADB와 필요한 DLL·고지를 로컬 `%LOCALAPPDATA%/CamFloatQA/android/platform-tools`에 준비했습니다. Google 저장소 메타데이터의 크기·체크섬으로 아카이브를 검증했습니다. 이후 사용자가 USB 연결을 승인한 휴대폰에서 `base.apk` 한 개(355,123,652바이트)를 확보했습니다. APK가 기존 256 MiB 제한보다 커서 실제 압축 구조를 확인한 뒤 상한을 512 MiB로 조정했습니다. 항목 수·전체 압축 해제 크기·개별 분석 크기의 제한은 유지합니다. 연결 준비 방법은 [Android 공식 안내](https://developer.android.com/tools/adb#Enabling)를 따릅니다.

APK와 분석 결과는 Git에서 제외된 `verification/current/android-app`에만 둡니다. 기본 보고서는 파일 체크섬·라이브러리 이름·고정된 키워드 표식을 기록합니다. 후속 DEX 분석은 실행 없이 함수 식별자·호출 관계·검토한 제어 속성과 수치만 기록하며 임의의 문자열·주소·키는 생략합니다. APK 원본과 제조사 라이브러리는 Git·릴리즈에 포함하지 않습니다. 이번 분석에서는 통신 캡처·앱 실행·카메라 조작·음성 전송을 하지 않았습니다.

#### C500GS APK 분석 결과

원본 APK SHA-256: `65ca4ac1f0cdaafa2a09643398fed37bc239d24b766dd518ea7f6787c64b9536`. DEX 21개와 네이티브 라이브러리를 데이터로 읽었습니다. `assets/appConfig.json`의 C500GS 항목은 `solution`과 `bindSolution`을 모두 `reoqoo`로 지정합니다. 일반 Gwell P2P와 IoTVideo 코드가 함께 있어 다른 기기용 코드와 구분해야 합니다.

- **OFF/ON:** Reoqoo 목록의 `DeviceListFragment.turnOnOrOffDevice` → `PluginManager.deviceEnOn` → `PluginServiceImpl.deviceEnOn` → `DeviceWriteModel.setDeviceCameraOnEn` → `DeviceManager.writePropertyOfDevice` 경로를 확인했습니다. 제어 속성은 `ProWritable.cameraOnEn.setVal`이며 IoTVideo 메시지 관리자로 전달됩니다. 다른 코드에서 발견한 `Action.cameraOn.stVal`을 이 경로와 혼동하지 않습니다. 속성 이름만으로 전원·마이크·스트리밍 차단을 보장하지 않습니다.
- **저장 위치:** 해당 플러그인에 `DeviceWriteModel.setDevicePreset` → `IIotWriteModelApi.writeDevicePreset` 경로가 있습니다. 위치 조회·이동·생성·삭제의 실제 메시지와 기기 응답은 아직 검증하지 않았습니다. 기존 ONVIF 프리셋 조회 실패를 해결한 것은 아닙니다.
- **말하기:** Reoqoo의 `GwIotLiveIntercom`은 IoTVideo `IIntercom.startIntercom`과 `endIntercom`을 사용합니다. 초기 설정은 AMR·8 kHz·160샘플 프레임·모노이며, 입력 비트 폭은 16입니다. 네이티브 통로는 `libiotvideomulti.so`의 JNI로 이어집니다. 앞서 시험한 RTSP 확장 PCM 후보와 같은 전송 방식이라고 볼 근거가 없습니다. 이 발견은 이전 테스트음의 미검출 원인을 확정하거나 실제 스피커 재생을 증명하지 않습니다.

정적 호출 경로와 모델 설정은 확보했지만 현재 펌웨어에서 실제 선택되는 분기·세션 인증·전송 패킷·복원 동작은 남아 있습니다. Android 라이브러리를 Windows EXE에 그대로 넣을 수는 없습니다. 다음 단계는 해당 모델의 SDK·프로토콜과 실제 명령·응답을 대조하는 것입니다. 앱 내부 계정 데이터나 키를 추출하지 않았고, 휴대폰에 캡처 앱·인증서·VPN을 설치하거나 설정하지 않았습니다.

#### 전용 인증·저장 위치 후속 조사

- **인증 경계:** `IoTSdkInitMgr.registerSdk`는 `accessId`·`accessToken`을 받아 `IoTVideoInitializer.register` → `IoTVideoInnerInitializer.nativeRegister`로 전달합니다. 제어 속성 쓰기는 `MessageMgrInternal.nExecuteModelCmd`로 이어집니다. 현재 확보한 제조사 앱 경로는 RTSP 계정만으로 직접 호출하는 API가 아닙니다. 토큰 값·휴대폰 계정 정보는 읽거나 복사하지 않았습니다.
- **저장과 이동 구분:** 위치 저장은 `ProWritable.presetPos` 속성 쓰기입니다. 앱 데이터 형식에는 `pos1`~`pos6` 슬롯과 위치별 `enable`·`posId`·`posName`·`x`·`y` 필드가 있습니다. 이는 앱의 데이터 구조이며 C500GS의 실제 지원 개수·저장된 위치를 확인한 것은 아닙니다. `OperationFragmentCmd.usePreset`의 이동은 위치 식별자를 별도 데이터 메시지에 담아 `IPluginPlayer.sendUserData`로 전달합니다. 저장 명령을 이동 명령으로 시험하지 않습니다.
- **Windows 경로:** 설치된 ipTIME CAM Multi 뷰어 1.30의 프로그램 폴더에는 libVLC·FFmpeg 계열 바이너리가 있고, 이 설치에서 IoTVideo 전용 Windows SDK는 찾지 못했습니다. [ipTIME 공식 답변](https://iptime.com/support/qna/892695)도 C500GS의 멀티뷰어 PTZ 미지원을 설명합니다. [Tencent의 기존 공식 개발자 문서](https://main.qcloudimg.com/raw/document/product/pdf/1131_42171_cn.pdf)는 PC SDK를 별도 제공하는 경로를 안내하지만, 현재 C500GS와 호환되는 Windows x64 패키지를 확보하거나 검증하지 못했습니다.
- **유사 공개 구현:** [Cryze](https://github.com/carTloyal123/cryze)·[Cryze v2](https://github.com/xerootg/cryze_v2)는 다른 제조사의 Gwell 기기용 조사 단서입니다. Android/ARM 라이브러리와 별도 실행 환경에 의존하므로 CamFloat에 바로 사용할 Windows SDK로 취급하지 않습니다. 해당 코드를 실행·통합하거나 네트워크 설정을 바꾸지 않았습니다.
- **추가 로컬 조회:** 등록된 내부망 기기 한 대에서 `GetServices`는 정상 SOAP 응답을 받았지만, 반환 목록은 이벤트 네임스페이스를 장치 서비스 경로에 연결한 항목 하나였습니다. 앞선 기능 정보와 서비스 분류가 일관되지 않습니다. 장치·PTZ의 `GetServiceCapabilities` 두 요청은 모두 응답 없이 종료됐습니다. 원문 주소·자격 증명 없이 `verification/current/camera-control/onvif-service-probe.json`에 기록했습니다. 이 조회에서는 렌즈 이동·저장 위치 변경·음성 전송을 하지 않았습니다.

**추후 조사 재개 시 확인 사항:** ipTIME에 C500GS·펌웨어 37.0.161의 로컬 제어 문서 또는 Windows x64용 SDK 제공 여부를 문의하는 방법이 있습니다. 필요한 범위는 렌즈 숨김/복원·저장 위치 조회/이동·양방향 음성과, 사용자 계정으로 접근 토큰을 발급받는 공식 절차입니다. 제조사 문의 외에도 앱의 실제 OFF/ON 통신 분석, 확보한 APK의 연결·명령 형식 추가 분석, ONVIF 호환 경로 조사가 후보입니다. 현재는 이 조사를 보류하고 기록만 보관합니다. 상하좌우 회전은 전용 계정 연동 없이 동작한 ONVIF 경로를 바탕으로 반복 조작·정지 처리를 검토하고 앱 통합을 준비합니다.

제조사에 확인할 항목은 다음과 같습니다. 문의는 아직 발송하지 않았습니다.

1. C500GS의 앱 OFF/ON과 같은 렌즈 숨김·복원을 외부 Windows 앱에서 실행할 공식 로컬 API 또는 SDK가 있는지.
2. 현재 각도·저장 위치 목록 조회와 저장 위치 이동을 ONVIF 또는 별도 API로 지원하는지. 지원한다면 서비스 경로·요청 예제·필요 인증은 무엇인지.
3. SDK가 있다면 Windows x64 지원, 일반 사용자 계정의 로그인·연결 절차와 무료 공개 앱의 배포·재배포 조건은 무엇인지.

제조사 답변을 기다리는 상태는 아닙니다. 현재 개발본에는 실제 동작을 확인한 ONVIF 경로로 상하좌우 조작을 통합했습니다. dev.2의 정지 요청 제거·길게 누르기 동작은 추가 실물 확인 대상입니다. 보류한 조사·음성 시험은 사용자 요청 후 재개합니다.

#### 네이티브 통신 코드 후속 분석

`libiotvideomulti.so`를 실행 없이 ELF·ARM64 코드로 분석했습니다. 속성 쓰기는 `MessageMgr.write_property_of_device`에서 `MessageHandle.send` 큐로 들어갑니다. SDK에는 `iv_send_service_msg`·`iv_send_passthrough_msg`의 서버/기기 전송 경로와 자체 P2P 패킷 처리·암호화 함수가 있습니다. 정적 호출 관계만으로 현재 C500GS가 어느 분기를 택하는지, 인터넷 없는 환경에서 어떤 인증으로 동작하는지 확정하지 않습니다.

말하기 시작·종료는 `Intercom.start_intercom`·`end_intercom`에서 `send_intercom_cmd`로 각각 1·0을 전달한 뒤 연결 객체의 명령 통로로 이어집니다. 이 수치는 SDK 내부 함수 인수이며 RTSP에 그대로 보낼 공개 명령 번호가 아닙니다. SDK의 로컬 HTTP 도움 기능도 발견했지만 카메라 OFF/ON용 API로 확인한 것은 아니며 요청하지 않았습니다. 사용자 토큰·계정 데이터·키 값을 수집하지 않았습니다. 결과는 Git 제외 경로 `verification/current/android-app/native-control-summary.json`에 정리했습니다.

### 말하기 전송 경로 조사

두 기기의 표준 음성 디코더·출력 설정 조회도 응답 없이 연결이 종료됐습니다. [공개 말하기 구현](https://github.com/realldz/yoosee-intercom)의 RTSP 확장 명령 형식을 후보로 시험했으며, 내부망 기기 한 대에서 `AudioCtlCmd:OPEN`·`CLOSE` 모두 `200 OK`를 받았습니다. 이 응답만으로 스피커 재생 지원이 확인된 것은 아닙니다.

청취 확인용 도구는 **`camera-speaker-test.bat`**입니다. 실제 마이크 대신 작은 합성 테스트음을 간격을 두고 반복합니다. 카메라 번호와 시작 대기 시간(0~300초)·전송 시간(1~30초)을 입력한 뒤 Enter로 시작합니다. 기본값은 10초 대기·3초 전송이며, T로 시간 변경·N으로 다음 후보 방식·Q로 종료합니다. 대기 후 연결 시간이 추가될 수 있습니다.

사용자 요청으로 아기방의 등록 내부망 기기에 30초 대기 후 5초 시험을 진행했습니다. 최초 시도는 연결 시간 초과로 0프레임이었고, 재시도는 250프레임을 보냈습니다. 사용자는 짧은 소리가 난 것 같다고 답했지만 반복 전자음을 확인한 것은 아니므로 성공으로 분류하지 않았습니다. 재시도의 종료 응답은 시간 초과였고, 음성을 추가 전송하지 않은 별도 닫기 요청에는 200을 받았습니다. 사용자 요청으로 다시 30초 대기·5초(250프레임)를 보낸 시험은 열기·닫기 모두 200이었지만, 사용자는 소리가 전혀 들리지 않았다고 확인했습니다. 스피커 재생은 미확인이며, 사용자 요청으로 음성 시험은 보류합니다. 사용자가 재개를 요청하기 전에는 추가 음성 시험을 하지 않습니다.

명령행에서도 `camera-speaker-test.bat --delay 20 --duration 5`로 지정할 수 있습니다. `--probe`는 첫 내부망 기기에 열기·닫기만 요청하며 음성 프레임을 전송하지 않습니다. 조회 결과는 `talkback-probe-latest.json`에 기록해 수동 청취 결과를 덮어쓰지 않습니다.

이전 자동 시험에서 카메라 한 대에 합성 테스트음 4초(200프레임)를 전송했고 OPEN/CLOSE 모두 `200 OK`를 받았습니다. 동시에 카메라가 보내는 음성을 메모리에서만 분석했지만 테스트음 두 주파수의 뚜렷한 증가는 검출되지 않았습니다. 전송 수락만으로 스피커 재생이 확인된 것은 아니며, 메아리 제거·실내 음향의 영향이 있어 미검출을 미지원의 증거로 단정하지도 않습니다. 이 자동 시험은 직접 청취로 확인하지 않았으며 이후 수동 시험의 관찰은 위에 별도로 기록합니다.

후보 전송 형식은 8 kHz 모노 PCM, 고정 길이의 벤더 프레임입니다. 종료·통신 실패·Ctrl+C 때 닫기 요청과 소켓 해제를 수행합니다. 결과는 로컬 `verification/current/camera-control/talkback-manual-latest.json`에 번호·응답·전송 개수·청취 결과만 기록합니다. 자동 음성 피드백 분석도 `speaker-feedback.json`에 수치만 남기며 원본 소리를 저장하지 않습니다. PC 마이크는 사용하지 않았습니다. 실제 사용자 마이크를 사용하는 기능과 앱 통합은 스피커 출력이 확인된 뒤 검토합니다.

도구의 닫기 요청은 [후보 원문](https://github.com/realldz/yoosee-intercom/blob/main/intercom.py)처럼 `/onvif1`을 사용하도록 맞췄습니다. `/onvif0`에서 열더라도 닫기는 별도 경로를 사용하며, 실제 닫기 전용 조회에서 해당 경로의 200 응답을 확인했습니다. 이는 종료 응답의 일관성이나 실제 스피커 종료를 보장한다는 뜻은 아닙니다. 새 수동 실행도 이전 청취 결과를 읽어 최근 30개를 보존합니다. 닫기 경로·중단 시 정리·청취 결과 보존 등을 포함한 가상 기기 검사 16개를 통과했습니다.

### 확인·개발 순서

1. 실제 모델·펌웨어와 서비스 주소·포트를 확인합니다. RTSP 포트를 제어 포트로 가정하지 않습니다.
2. 기기를 움직이지 않는 기능 조회부터 진행합니다. 지원이 확인된 명령만 짧게 시험합니다.
3. 방향 제어는 버튼 해제·앱 전환·조작창 닫기·연결 끊김 때 정지하도록 설계합니다. 기존 방향키의 화면·카메라 전환과 충돌하지 않게 합니다.
4. 렌즈 숨김과 복원 위치를 확보하고 두 위치 간 이동을 검증합니다. 이 기능은 영상·마이크·전원 차단을 보장하지 않습니다.
5. 음성 시험은 사용자 요청으로 보류합니다. 재개 후 스피커 출력을 확인하면 마이크는 누르는 동안만 전송하는 방식부터 검토합니다. 대상 카메라와 전송 상태를 표시하고 버튼 해제·앱 전환·종료·연결 끊김 때 중단합니다.
6. 실제 지원이 확인된 기능부터 구현하고 기능별 검사를 진행합니다. 다음 릴리즈 직전에 전체 QC와 배포 EXE를 확인합니다.

참고: [ipTIME 제품 안내](https://www.iptime.com/products/961) · [RTSP 접속 안내](https://www.iptime.com/support/faq/26651) · [ONVIF Profile T](https://www.onvif.org/profiles/profile-t/).

시험 주소·계정·비밀번호와 실제 영상은 공개 문서·이슈에 기록하지 않습니다. 검사 운영 방식은 [개발 안내](development.md)에 정리했습니다.

## 소리 증폭

카메라 제어 조사 다음에 검토합니다. 현재 최대 음량은 100%이며 150%·200% 증폭은 아직 제공하지 않습니다.

1. 합성 음원으로 실제 증폭량, 잡음 증가와 소리 찢어짐을 측정합니다.
2. 화면별 음량·음소거가 독립적으로 유지되는지, 확대·재연결 후에도 값이 유지되는지 확인합니다.
3. 기본 범위는 0~100%로 두고 증폭을 별도로 켤지 검토합니다. 100% 지점을 쉽게 구분하고 작은 슬라이더에서도 조절할 수 있도록 합니다.
4. 로컬 설정 저장·이전 설정 읽기와 필요시 출력 제한 처리를 함께 점검합니다. `.camfloat` 파일에는 계속 음량·음소거를 넣지 않습니다.

구현 검토: [libVLC DirectSound 출력 코드](https://github.com/videolan/vlc/blob/3.0.23/modules/audio_output/directsound.c).
